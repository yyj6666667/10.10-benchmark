# 10.10 benchmark

The current single-node, full-parameter fine-tuning benchmark runs only on
qj5090, reached through the sap1 SSH jump host. Older host analyses remain
in `references/` for context and are excluded from the current chart.
Results and small run evidence are kept in the private GitHub repository
`yyj6666667/10.10-benchmark`.

## Contents

- `references/`: copies of the two user-provided historical test analyses.
  Their tables are **historical results**, not results of the current sweep.
- `results/historical_throughput.csv`: machine-readable step time and TPS
  extracted from those analyses by `tools/extract_historical.py`. It keeps
  `pytorch_torch` distinct from the figure's `pytorch_onednn` backend.
- `results/current_throughput.csv`: completed new throughput measurements.
- `results/qj5090_figure9.csv`, `.png`, and `.svg`: the current qj5090
  comparison, generated by `tools/render_qj_figure9.py` solely from new
  qj5090 measurements. Blank chart positions mean no completed measurement;
  a red cross is reserved for an observed OOM with a recorded evidence path.
- `results/semantic_checks.csv`: fixed-batch loss checks; these are not
  throughput measurements.
- `runs/kt-2026-10-10/`: small raw KT evidence: run configurations, software
  versions, timing, logs, and the isolated Qwen text-path patch. No model
  weights or optimizer checkpoints are included.
- `tools/fsdp2_onednn_full_ft.py`: PyTorch FSDP2 + oneDNN CPU expert baseline.
- `runs/pytorch-fsdp2-onednn-2026-10-10/`: run configuration, per-step timings,
  environment versions, resource monitor, and loss evidence for this baseline.

## Measurement convention

For eight-GPU server throughput, global batch size is 8. Completed KT cases
used 15 optimizer steps, with the first 5 excluded. New runs use 8 steps,
with the first 2 excluded. TPS is `8 * sequence_length / mean_step_seconds`
over the measured steps. The GLM KT semantic check repeats four examples on
four GPUs. Qwen KT, MegaTrain, ZeRO, and FSDP2 semantic checks repeat eight
examples on eight GPUs. Semantic checks must not be plotted as
throughput.

The FSDP2 + oneDNN baseline uses eight data-parallel ranks. FSDP2 shards the
GPU trunk while each rank owns a disjoint set of CPU experts. Expert
assignments use differentiable Gloo all-to-all; each owned expert uses
oneDNN-backed BF16 CPU linear layers.
GPU and CPU master parameters are FP32, compute is BF16, CPU AdamW moments
are BF16, GPU AdamW moments are FP32, and the global gradient norm is clipped
to 1.0. The learning rate starts at 1e-5 and follows a cosine schedule. Its
forward, backward, and optimizer host-wall timers synchronize CUDA at each
boundary, so phase times have a different boundary from the historical
coarse-host-wall KT runs.
Activation checkpointing covers the GPU attention, linear attention, and MLP
submodules. CPU routed experts and Gloo all-to-all remain outside the
checkpoint, because replaying those collectives can change their order across
ranks. The revised sweep stashes completed CPU gradients in BF16 while
retaining FP32 expert master weights. Its AdamW update works on bounded chunks
and releases each gradient after updating that parameter. Earlier GLM rows
from the uncompressed implementation remain in the raw CSV until each length
is rerun; the chart uses the latest completed case. Compare configuration
checksums before interpreting the raw CSV as one uniform series.
On qj5090, seq4096 also moves dense GPU AdamW moments to CPU between steps.
The moments return to GPU for each fused optimizer update; their FP32 values
and the AdamW computation are unchanged. GLM seq4096 reached the 20 GiB host
memory reserve during step 2, so it has no valid throughput measurement.
The earlier GLM seq1024 memory failure was resolved by BF16 gradient storage;
the revised 1024 and 2048 cases both finished all eight steps.
After GLM seq4096 reached the host-memory guard, later long-sequence cases
recompute only the CPU expert linear block in backward. This block contains no
collective; a two-rank Gloo check matched outputs and input/weight gradients
exactly with and without recomputation. The per-run configuration records
whether CPU expert checkpointing was enabled. It applies to Qwen seq512 and
above, and to any later GLM seq4096 retry; earlier completed rows are unchanged.
CPU expert weights are unbound once per group before the expert loop. This
lets autograd assemble each full weight gradient once rather than zeroing a
full parent gradient for every expert selection. The seq2048 one-step profiler
comparison is recorded in `results/qj5090_glm_fsdp2_onednn_seq2048_profile.md`.
The first Qwen seq4096 attempt hit CUDA OOM while the default causal loss
converted the full logits tensor to FP32. The seq4096 retry computes the same
cross entropy in 128-token chunks and recomputes each chunk in backward, so
the full FP32 logits copy is never live. The run configuration records this
option; a BF16/FP32 reference check matched loss within 7.6e-6 and gradients
exactly on a small masked test case.

An earlier GLM KT 4096 diagnostic ran while another service occupied GPU 0;
it is excluded from this chart. The clean qj5090 retry succeeded and its
configuration, timing, resources, and log are preserved under
`runs/kt-qj5090-20261010/glm_sweep/`.

Model checkpoints, adapter weights, optimizer state, and regenerable training
checkpoints are excluded from this data repository.

## qj5090 KT rerun

The qj5090 rerun uses `/mnt/hurry-bench` on the remote host. The base KT
training source is the clean `bfe3e57c` snapshot with the exact BF16 gradient
norm patch from KT `fa04bb2` applied. Updated Accelerate `9a0d243` and
Transformers `e04dcff` are loaded through an isolated `PYTHONPATH` overlay.
The existing LLaMA Factory `36b12fd0` is copied into the benchmark overlay
with a two-line optimizer-method signature fix so its override accepts the
model argument passed by the KT Trainer path.
The built KT wheel is also installed only in that overlay. Source revisions
and the patch are in `tools/kt_qj_source_revisions.md` and
`tools/kt_grad_norm.patch`.

Run one GLM case on qj5090 with `tools/run_qj_kt_case.sh SEQ 15`. Each case
uses eight GPUs, BF16 full fine-tuning, global batch 8, gradient clipping at
1.0, and 15 steps with the first five excluded. Timing follows the earlier
KT host-wall phase timer, with no forced CUDA synchronization. The GPU peak is
the largest `nvidia-smi` used-memory sample over the eight cards. CPU RSS is
the peak sum of the benchmark process tree's RSS, so shared pages can be
counted more than once. Both resource measurements are sampled every two
seconds. Each successful case writes `performance.csv` with the requested
eight columns and appends its row to `/mnt/hurry-bench/results/{model}_kt_performance.csv`.
No model or optimizer checkpoint is retained.

`tools/run_qj_glm_kt_sweep.sh` queues GLM lengths 32, 64, 128, 256, 512,
1024, 2048, and 4096 on qj5090, stopping at the first failed case. After
seq32 it runs a fixed-batch seq512 loss check before continuing. The sweep
sets 64 OpenMP threads on rank 0 for KT gradient clipping and zero data-loader
workers to avoid forking processes that hold the CPU model. Its background
log is `/mnt/hurry-bench/logs/glm-kt-sweep-20261010.log`; each case retains
its configuration, timing, resource summary, and training log under
`/mnt/hurry-bench/runs/`.

GLM KT lengths 32–4096 have completed. `tools/run_qj_qwen_kt_queue.sh`
validated Qwen's fixed-batch loss descent before starting its eight lengths.
The ZeRO-3 optimizer-offload preflight reached qj5090's host-memory guard on
GLM and observed CUDA OOM on Qwen. The revised PyTorch FSDP2 + CPU oneDNN
sweep now runs, followed by MegaTrain's isolated GLM diagnostic, GLM sweep,
and Qwen sweep. MegaTrain's earlier GLM first-step loss was non-finite; the
follow-up restores per-layer router buffers when reusing a GPU layer template.
The Qwen oneDNN fixed-batch check passed with loss 4.0037 to 0.1714.
Completed
cases use eight steps and two warmup steps, with one fixed-batch loss check
per model and backend. `tools/watch_qj_results.sh`
syncs each completed result table or observed failure, regenerates the chart,
and pushes it to the private repository. The queues wait for the active GPU
job to exit before launching the next framework.

The GLM seq4096 gradient-clipping PyTorch profiler comparison and both local
Chrome traces are under `runs/kt-qj5090-20261010/profiles/`. The fused BF16
path removed the long `aten::item`, while raising rank 0's OpenMP threads from
2 to 64 reduced the measured clipping window from 37.9 to 4.3 seconds.

The official ModelScope `Qwen/Qwen3.5-122B-A10B` checkpoint downloads to
`/mnt/data/models/Qwen3.5-122B-A10B` with
`tools/download_qwen_bf16.py`. Its Qwen text-decoder path correction is
isolated in `/mnt/hurry-bench/py-overlay-qwen` and recorded as
`tools/qwen_text_path_contract.patch`. A Qwen case uses
`tools/run_qj_kt_case.sh SEQ 15 qwen`; the no-training preflight is under
`runs/kt-qj5090-20261010/preflight/`. Both model downloads finished before
GLM timing began, so download I/O did not affect timing. The Qwen transfer
was paused until GLM finished; `tools/resume_qwen_after_glm.sh` resumed it
after the GLM success marker.
After GLM, `tools/wait_qj_glm_then_run_qwen.sh` runs a fixed-batch Qwen loss
check, then the eight Qwen sequence lengths in order. The loss check must
finish with finite gradients and a lower final loss before Qwen throughput
measurements begin. `tools/verify_qwen_bf16_checkpoint.py` inspects shard
headers and rejects FP8 tensors before training.

MegaTrain uses the official `infinity` CPU-master source extracted under
`/mnt/hurry-bench/src/megatrain`. Its benchmark harness loads the text-only
106.85B or 122.11B model, uses eight GPU worker processes and BF16 CPUAdam
states, and verifies fixed-batch loss descent before throughput is accepted.
ZeRO uses DeepSpeed 0.19.1 stage 3 with optimizer state offloaded to CPU and
parameter shards on GPU, matching the historical offload layout. BF16 master
gradients and optimizer states remain enabled. The exact config is
`tools/zero3_cpu_offload.json`; qj5090's 32 GiB GPUs are smaller than the
historical 48 GiB cards, so each sequence requires a fresh result or a
recorded failure.

## qj5090 FSDP2 + oneDNN baseline

`tools/run_qj_fsdp2_onednn_case.sh glm45_air 32` launches the GLM seq32 case
after all eight GPUs are free. Use `qwen35_122b` for the Qwen model; its 39
BF16 checkpoint shards have been verified. The runner checks every shard,
records source checksums and environment versions, and refuses to start when
a GPU is occupied. It imports the same isolated Transformers and LLaMA Factory sources
used by the KT benchmark. A no-GPU launch preflight is recorded under
`runs/pytorch-fsdp2-onednn-qj-20261010/preflight/`; it is not a throughput
measurement.
